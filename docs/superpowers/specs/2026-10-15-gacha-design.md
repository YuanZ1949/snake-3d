# 抽卡（祈愿）系统设计 Spec

日期：2026-10-15
状态：已获用户批准（对话内分节设计 + 星级分界表）
流程：brainstorming → architectural（本 spec）→ writing-plans → 实施

## 1. 目标与意图

用户原话：「我想增加功能 给游戏增加一个抽卡界面用于抽"蛇"的皮肤 样式参考原神 消耗积分抽卡 点击后弹出一个流星从侧边往另外一边下落闪光最后展示抽到的角色的图片」。

给游戏加一套完整的祈愿（抽卡）子系统：以「吃果星尘」为货币、原神规则的概率与保底、CSS 流星动画演出、程序化生成的蛇皮肤与立绘卡。目的是给休闲对局加一条长线循环：打局攒星尘 → 抽皮肤 → 带皮肤进局炫耀。

## 2. 已拍板决策（用户逐项确认）

| 决策点 | 结论 |
|---|---|
| 货币来源 | 方案 C 混合：账号星尘总账（局末按吃果 1:1 结算入账）+ 单局当场星尘（局内可直接消费，死亡/离开并入总账不作废） |
| 稀有度分档 | 三档：★★★ 蓝 / ★★★★ 紫 / ★★★★★ 金，流星与爆闪颜色随档变化 |
| 概率与保底 | 原神原版规则：5星 1.6%、90 抽硬保底、50/50 大保底；4星 13%、10 抽必出 |
| 定价 | 160 星尘/抽、1600/十连（无折扣） |
| 素材 | 全部程序化生成（蛇皮肤纹理 + 立绘卡均 canvas 生成），零外部图片依赖 |
| 登录门槛 | 抽卡必须登录账号（积分与库存挂账号），未登录点抽卡引导登录 |
| 动画技术 | 方案 1：CSS 流星雨（容器旋转 + 渐变拖尾 + 伪元素星头 + 爆闪 keyframe），不用 three.js / canvas 粒子 |
| 抽卡入口 | 随时可用（含单局内） |

## 3. 卡池构成

单池「常驻祈愿」，共 11 款新皮肤（扩充客户端 SKINS 数组；**现有 5 款保留为免费默认池，人人可用、不入卡池**）。

| 星级 | 数量 | 皮肤名单 | 视觉特征 |
|---|---|---|---|
| ★★★ | 6 | 赤霞、青岚、墨影、鎏银、樱粉、沙金 | 换色系，复用现有纹理语言（diamond/wave/spot/crack） |
| ★★★★ | 3 | 星河（渐变星空纹）、雷纹（闪电纹）、霜纹（冰晶纹） | 新图案 + 轻金属反光 |
| ★★★★★ | 2 | **UP 限定「辉夜」**（金黑渐变 + 自发光描边）+ 常驻「白金圣蛇」（白金双色 + 全身微光） | 蛇身 emissive 脉动发光（新能力） |

5星价值锚点 = 蛇身动态发光特效（现有材质没有），作为炫耀信号。

## 4. 经济与概率规则

### 4.1 星尘
- **总账**：挂账号（Store users JSON 持久化字段）。每局结束按该玩家本局吃果数 ×10 星尘结算入账（需登录才入账；未登录不累积总账）。
- **当场星尘**：局内吃果实时累计（**每果 +10，bonus 星星同 +10；场上多果并存，果数 3-8 随地图放大**）；局内祈愿界面可直接消费。死亡/离开房间时，当场星尘一次性并入总账（不作废、不双计）。当场星尘消费后从当局未结算额中扣除，局末只结算余额。
- 客户端展示：总账余额 = total + 当场未消费部分。

### 4.2 概率（每次单抽；十连 = 10 次独立单抽）
- 5星 1.6%、4星 13%、3星 85.4%（含保底覆盖后的实际分布另算）。
- **4星保底**：连续 9 抽无 4星及以上，第 10 抽必出 4星（若当抽已出 4/5星则计数清零）。
- **5星硬保底**：第 90 抽必出 5星，出后计数清零。
- **50/50 大保底**：出 5星时先掷 50% 给 UP「辉夜」；若歪出常驻「白金圣蛇」，则下一次 5星**必为 UP**，出 UP 后重置。UP 状态存账号。
- **十连**：1600 一次结算 10 抽，保底计数逐抽累计，服务端逐抽串行判定。

### 4.3 重复返还
已拥有的皮肤再次抽到 → 不入库存，返还星尘：3星 10 / 4星 50 / 5星 200。

## 5. 服务端设计（serve.py）

### 5.1 数据（Store users JSON 扩展字段，防御式读取兼容旧账号）
```
user 字典新增:
  'stardust': int           # 星尘总账
  'skins': [int, ...]       # 已拥有皮肤 id（SKINS 下标）
  'gacha_p5': int           # 距上次5星的抽数（保底计数）
  'gacha_p4': int           # 距上次4星的抽数
  'gacha_lose': bool        # 50/50 是否已歪（下个5星必 UP）
```
局内当场星尘：Session/Player 上挂临时字段（不持久化，死亡/离房时并账）。

### 5.2 消息协议（新增两条，均需已登录）
- `{t:'gacha', n:1|10}` → 余额不足回 `error`；成功回 `{t:'gachares', items:[{skin, star, dup, refund}], balance, gained}`（items 顺序 = 抽取顺序；客户端负责压轴排布展示）。
- `{t:'gachainfo'}` → `{t:'gachainfo', balance, skins:[...], p5, p4, lose}`（进祈愿界面时拉取；局内 balance 含当场星尘）。

> **回写（实现偏离，Task 3 落地 `df660ac`）**：
> ① items 每项增加 `up` 字段（`{skin, star, up, dup, refund}`）——十连展示需要标 UP；回包与 gachainfo 均增加 `dust` 字段（当场星尘）。
> ② `balance` 语义改定为**纯总账**（`store.stardust`，不含当场星尘），当场星尘由独立 `dust` 字段承载——原「局内 balance 含当场星尘」废弃，客户端余额展示按 `balance`（可花）与 `dust`（局内临时，settle 并账）分离。
> ③ gacha 加固（oracle 审查 BLOCKER 修订）：`n` 白名单只收 1/10（防负数变加币）；入局玩家 `p.user` 与登录账号不一致回 error；检查→扣减→save 全程无 await（同账号双开会话无法在关键区穿插）。大厅（无房）允许抽卡，`dust=0`。

### 5.3 逻辑单元（可测函数）
- `def gacha_roll(rng, p5, p4, lose5050, pity5, pity4) -> (star, skin_id, new_state...)`：纯函数，rng 可注入（测试打桩），返回结果与新保底状态。UP 判定与皮肤选取（同星随机，UP 只在 5星参与）在此函数内。
- `def stardust_grant(user, eaten)`：局末结算入账。
- 局内当场星尘消费顺序：先花当场星尘，不足再从总账扣（或反之——**定死为：先总账后当场，实现简单且死亡并账路径单一**）。

> **回写（实现偏离，Task 2 落地 `e3d721b`）**：`gacha_roll(rng, lose5050, pity5, pity4)` **4 参**，只返回 `{'star','up','pity5','pity4','lose5050'}`（不含 skin_id）；**皮肤选取拆出为独立 `pool_pick(rng, star, up)`**，由 `handle_gacha` 逐抽循环调用（与 gacha_roll 共用同一 rng）。偏离原因：拆开后两个纯函数各自最小可测（11 项单测覆盖判定序/保底/5050/池选取），且逐抽循环中保底状态可即时回写 user 字段。消费顺序实现 = 定死方案（先总账后当场：`pay_total=min(total,need)`、不足部分扣 `p['dust']`）。`stardust_grant` 落地为 `settle_dust(p)`（局末并账，挂 win_pending 六处含平局）。

## 6. 客户端设计（index.html）

### 6.1 祈愿界面（全屏覆盖层，风格贴原神：深蓝金装饰）
- 入口：顶栏 chip「✨ 祈愿」。未登录点击 → 弹提示引导登录。
- 布局：顶部星尘余额；中部卡池横幅（UP「辉夜」立绘 + 倒计时文案占位）；底部两个按钮「祈愿 ×1」「祈愿 ×10」；右侧页签「我的皮肤」。
- 「我的皮肤」：按星级分组展示已拥有皮肤（程序化缩略图），点击选用（沿用现有 skin 同步协议扩字段：`{t:'skin', i}`，SKINS 下标含新 11 款）。免费 5 款始终可选。

### 6.2 抽卡动画（核心演出，CSS 为主）
- 覆盖层状态机：`idle → meteor(0.9s) → flash(0.35s) → reveal`。
- **流星**：`.meteor-layer` 容器 `rotate(-25deg)`，流星 = 主条（`linear-gradient` 拖尾 + `drop-shadow` 光晕）+ 伪元素星头；从屏幕右上外侧 translate3d 飞入至撞击点（左下偏中）。颜色按结果最高档（金 > 紫 > 蓝）由 JS 注入 CSS 变量。
- **爆闪**：撞击点 `radial-gradient` 白光 keyframe 由小到大全屏扩散（0.35s），随后卡片翻出（`rotateY` 3D 翻转）。
- **单抽**：1 张立绘卡翻出（档位徽章 + 名字 + 重复返还提示）。
- **十连**：爆闪后 10 格依次翻开（间隔 120ms），**最高档卡最后压轴翻**；底部一排缩略图；点击任意处跳过剩余动画直接看结果。
- 动画期间锁输入，`prefers-reduced-motion` 时跳过流星直接 reveal。

### 6.3 立绘卡与 5星特效
- `makeCardArt(skin)`：canvas 256×384——渐变底（按星级：蓝/紫/金光晕）+ 蛇形剪影（贝塞尔曲线，取皮肤配色）+ 星级徽章 + 名字条。
- 5星蛇身 emissive 脉动：SKINS 新增 `glow: true` 字段，材质 `emissive` 随时间正弦脉动（渲染循环里驱动，仅限拥有并选用的玩家端生效——皮肤选择沿用现有同步，其他客户端也会看到发光，符合炫耀目的）。

### 6.4 局内当场星尘
- 局内 HUD 显示「✨ 当场星尘: N」（吃果 +10，星星 +10）；祈愿界面内显示「总账 X + 本局 Y」。
- 死亡/离开时客户端不需特殊处理——服务端并账，客户端刷新余额即可。

## 7. 局末结算与并账（服务端事件点）
- 对局结束（`win` 分支结算）与玩家死亡/离开：`stardust_grant` 入总账（仅登录用户），当场星尘字段清零。
- 未登录玩家：当场星尘仅 HUD 显示（未登录不可抽，§2 已拍板）；死亡/离房时当场星尘**直接丢弃不入账**（当场星尘挂 Session，不跨局）。登录玩家死亡/离房时余额部分并入总账。

## 8. 测试计划

### 8.1 单元测试（test_game.py，TDD 先红后绿）
1. `test_gacha_roll_rng_distribution`：打桩 rng，验证概率分支与保底触发。
2. `test_gacha_pity90_hard`：pity 计数到 90 必 5星，出后清零。
3. `test_gacha_pity10_four`：连续 9 抽 3星，第 10 抽 ≥4星。
4. `test_gacha_5050_guarantee`：lose=True 时 5星必 UP；出 UP 后 lose 重置。
5. `test_gacha_insufficient_balance`：余额不足回 error，库存/计数不变。
6. `test_gacha_dup_refund`：已拥有皮肤返还对应星尘，库存不变。
7. `test_stardust_settle_on_end`：局末按吃果数入总账；当场字段清零。
8. `test_gacha_requires_login`：未登录发 gacha 回 error。

### 8.2 前端探针（Playwright，test-results/ 备份 Temp\opencode）
- 建号 → 喂星尘（打桩或服务端注入）→ 开祈愿 → 单抽：动画状态机走完（meteor→flash→reveal）errors=0、余额扣减、卡片出现。
- 十连：10 卡全出、最高档压轴、跳过生效。
- 未登录点击 → 登录引导提示。

## 10. 风险与备注
- index.html 已 3400+ 行，抽卡 UI 会再加约 400-600 行（CSS+JS）——保持单一覆盖层组件、不重构既有 UI。
- 服务端概率必须服务端判定（客户端只播动画），防伪造 `gachares`——余额/库存/保底全在服务端，客户端消息不可信。
- 90 抽保底 + 160/抽 = 最坏 14400 星尘一发 5星；需核对一局产出（实现前从 serve.py 现有吃果得分与对局时长估算，若产出过低在实施计划里回调定价或果数，不改已拍板的相对结构）。
- Store JSON 无版本号：新增字段一律防御式读取（`u.get('stardust', 0)`），旧账号无缝兼容。
